# 治理原则与说明文件

用于起步搭建、建立规范和整体整理。“治理”指决定谁做什么、怎样接受改动、如何发布和继续维护。先形成能执行的约定，再决定放入哪些文件。

## 从项目当前阶段开始

| 阶段 | 本阶段需要讲清的事 | 增加下一层的信号 |
| --- | --- | --- |
| 个人起步 | 用途与边界、使用入口、怎样验证和保存版本、下一步 | 作者反复忘记步骤，或别人开始使用/参与 |
| 持续开发或小团队 | 模块职责、贡献方式、改动验收、决策与维护责任 | 多人改动互相影响，或开始稳定发布 |
| 有外部使用者/贡献者 | 支持范围、兼容性、发布说明、问题与安全反馈入口 | 维护量增长，需要明确分工和交接 |

阶段可交叠，不根据 stars 决定治理强度。独立开发但已被他人依赖的库也需要兼容性说明。只要少量约定够用，就放在现有 README；文件增多必须对应实际读者和维护任务。

## 将原则写成可执行约定

| 原则 | 需要明确的实际做法 | 新手可观察的结果 |
| --- | --- | --- |
| 目标与边界明确 | 写清解决的问题、当前可用能力、已知限制；计划与已交付分开 | 能判断一个需求是否属于项目范围 |
| 一份事实来源 | 指定配置、命令、版本和接口说明的来源；其他位置链接或生成 | 修改后不必猜哪份文档是真的 |
| 改动小且可追踪 | 每次改动说明目的、验证与相关问题；关键决策留下简短原因 | 日后能查明为什么改、如何撤回 |
| 主分支保持可用 | 约定适用的通过条件；修复失败后再合并相关改动 | 拉取主分支能按已声明步骤使用 |
| 决策与责任清楚 | 谁决定范围、谁评审/合并/发布、谁回复问题；沿用已有授权 | 不会出现规则要求一个实际不存在的人批准 |
| 验证可重复 | 记录环境与检查入口，变更时同步更新；解释未验证部分 | 作者和协作者能得到可比较的结果 |
| 发布考虑使用者 | 标明版本变化、兼容影响和必要迁移步骤，检查实际产物 | 用户能知道是否该升级以及怎么升级 |
| 规则可以维护 | 文档有明确维护责任与更新触发点，失效说明及时调整 | 项目变动后规则仍与实际一致 |

这张表不是要求新增审批、机器人或测试平台。个人项目可以由作者承担决策、评审和发布；改动自查与真实验证仍有价值。提交与恢复的具体操作见 [Git 操作指南](git-workflows.md)，检查和发布细节见 [整理判断与验收标准](repository-standards.md)。

合并条件应贴合现有项目：相关检查、必要的人工验证和实际可用的评审者。只有用户要求配置远端治理且授权范围明确时，才设置规则。`CODEOWNERS` 可以表达评审责任；是否强制评审还取决于远端规则，不能因为文件存在就宣称已强制执行。参见 [GitHub CODEOWNERS 文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)。

遇到重大取舍，如更换数据存储、公开 API、仓库边界或支持平台，记录上下文、选择、原因和后果。小项目可以留在一个现有设计说明中；需要长期追踪多次决策时再使用 ADR（架构决策记录）。已失效的决策标明被何项替代，保留理解历史所需的信息。[Michael Nygard：记录架构决策](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

## 说明文件怎么选

先检查现有文件、链接和托管平台显示的继承规则。GitHub 项目可能从所属账户的公共 `.github` 仓库继承贡献与社区文件；本地没看到文件不等于没有规则。不能将“补文件”变成无意覆盖已有规定。继承文件不会自动包含在本地克隆中；本地必要步骤仍要有可访问的入口。[GitHub 默认社区文件说明](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)

逐项给出“现在需要 / 条件满足再加 / 当前无需”，不要把下表当作批量生成任务。保留现有命名和路径；`docs/ARCHITECTURE.md` 等是可选惯例，不是跨生态标准。

| 文件或位置 | 主要读者与职责 | 最少有用内容 | 创建或拆分时机 |
| --- | --- | --- | --- |
| `README.md` | 首次使用者和未来的作者 | 项目用途、状态、最短使用路径、实际示例、必要限制与文档入口 | 大多数需要长期保留或分享的项目先有它 |
| `CONTRIBUTING.md` | 改代码、文档或数据的人 | 环境、开发与检查命令、如何报告问题和提交改动 | 开始接受贡献，或开发说明使 README 过长 |
| `AGENTS.md` | 在仓库工作的编码代理 | 已验证命令、目录约定、容易犯错的边界及任务相关限制 | 反复使用代理且确有项目特定指导；已有文件优先维护 |
| `docs/ARCHITECTURE.md` | 需要理解系统的开发者 | 模块职责、主要依赖/数据流、关键边界、任务入口 | README 的目录说明不足以支持修改 |
| `docs/decisions/` 或现有决策说明 | 将来复查方案的人 | 日期/状态、上下文、选项、决定、原因与后果 | 重大选择需要长期解释或多人达成约定 |
| `CHANGELOG.md` 或发布说明 | 使用已发布版本的人 | 影响用户的新增、修复、破坏性变化与迁移入口 | 开始持续发布；选择一个主要记录位置 |
| `LICENSE` / 既有许可证文件 | 需要使用或分发项目的人 | 用户选定的授权文本与准确版权信息 | 需要明确授权时处理；沿用已有选择，不擅自默认许可证 |
| `SECURITY.md` | 报告漏洞的人 | 真实支持范围、可用的私密反馈路径 | 有外部使用者且维护者能承接反馈；不虚构邮箱或响应承诺 |
| `CODE_OF_CONDUCT.md` | 社区参与者 | 行为边界、举报渠道及实际处理责任 | 有社区互动并具备执行能力时 |
| `MAINTAINERS.md` / `GOVERNANCE.md` / README 维护段落 | 贡献者与维护者 | 谁决策、评审、发布、接手；分歧如何处理 | 多人责任不清或需要交接；个人项目通常一段话够用 |
| `ROADMAP.md` / 现有项目看板 | 关心方向的人 | 当前重点、候选想法与已承诺事项的区别 | 确需公开方向或协调优先级；不把愿望写成工期承诺 |
| `SUPPORT.md` / README 求助段落 | 遇到使用问题的人 | 使用问题、缺陷、安全反馈分别去哪 | 存在不同反馈渠道时再拆分 |
| `docs/OPERATIONS.md` 或运行说明 | 部署与运行系统的人 | 环境、启动停止、日志、必要备份与恢复、负责人 | 项目真的有部署或持久化服务；不凭空生成运维流程 |
| `.github/ISSUE_TEMPLATE/` 与 PR 模板 | 报告者、贡献者、评审者 | 复现信息；改动目的、验证与关联问题 | 反复缺少相同信息，模板能降低沟通成本时 |
| `.github/CODEOWNERS` | 有明确分工的评审者 | 已核实的路径和负责人 | 多人需要自动分配评审；核实账号和权限再配置 |

`.gitignore`、依赖清单、锁文件、格式和 CI 配置是执行规则的配置文件，另按技术栈选择，不用说明文档代替其生效机制。`.env.example` 只在项目确有环境变量配置时提供，使用假值并说明必填项。具体核查见整理判断与验收标准。

MIT 等属于代码许可证；网站的使用条款、隐私政策另按实际产品需求处理，不能互相替代。按 [元数据、许可证与徽章检查](metadata-and-badges.md) 核对授权文本、版权信息、包元数据及 README 的对应关系；已有明确选择不重复索要确认，本轮需要新增授权但缺少选择时只询问这一决定并继续其他整理。

## 怎样写到真正可用

先问四件事，再决定篇幅：谁要读、读完要完成什么、哪些事实已有证据、什么变化会让它过时。

- **README**：让新用户完成一次真实使用。没有可运行程序的知识库，应能找到和使用一条内容；起步阶段明确标为未实现的计划，不写虚构启动命令。
- **贡献说明**：说明在哪个目录执行什么命令、预期看到什么、失败去哪里排查。语言和工具版本来自项目，不从样板凭空填。
- **架构说明**：解释结构及关键联系，举一个实际改动路径。几个文件的项目用简短文字或目录说明即可；不机械补数据库、队列和多层架构。
- **治理说明**：选择实际可执行的规则并明确责任。角色、权限、联系渠道、兼容承诺不确定时，先完成已知部分，再询问影响执行的决定。
- **AGENTS.md**：记录项目特有的命令与边界，链接现有开发资料；不要重复人类文档全部内容、放入凭据或要求代理忽略用户指令。

保持核心信息一处维护，其他文档提供链接。例如 README 指向开发说明，架构说明指向决策记录；不在四份文件重复一套安装命令。文档较少时由 README 直接导航，材料确实多了才建立单独文档索引。

## 把文档更新放进日常工作

| 实际变化 | 同步检查的说明 |
| --- | --- |
| 入口、安装、运行命令变化 | README 与开发说明中的对应步骤 |
| 配置项变化 | 配置样例、默认值来源与使用说明 |
| 运行环境或支持范围变化 | 版本声明、开发环境、CI 范围、README 前置条件与版本徽章 |
| 包名、版本、授权或发布地址变化 | 包元数据、许可证及声明、发布说明、README 各语言版本与相关按钮 |
| 模块职责或路径变化 | 任务导航、架构说明、相关链接 |
| 行为或接口变化 | 实际示例、相关测试与必要兼容说明 |
| 发布或维护责任变化 | 变化说明、发布步骤、维护与反馈入口 |

只更新被实际影响的内容，不要求每次代码修改都改所有文档。完成后验证链接、命令来源和读者的使用路径；没有真实内容的章节删除或明确标记为尚未实现的计划，不交付成片占位符。

对已部署且有数据的项目，核实备份范围、恢复前提与可接受的数据损失；没有实施和恢复演练证据时，只能交付恢复方案，不能宣称已具备恢复能力。远程 Git 不能代替未提交文件、外部数据和密钥的备份。

交接或停止维护时更新状态、最后验证的使用方式、必要负责人/替代入口和已知限制。是否归档远端仓库、移交权限或关闭服务由用户决定，不因整理文档自动执行。

## 交付格式与边界自查

方案中用一张小表列出本轮选中的文件：实际路径、为什么现在需要、准备写什么、何时更新。随后按授权落实内容，并给出一条“修改 → 验证 → 保存版本 → 同步说明”的实际路径。

- 新人只有一个脚本：简短说明和真实运行方式即可起步，不预建完整治理文件夹。
- 已有框架应用：遵循实际结构与配置，补缺失入口及约定，不套用另一套目录。
- 私有笔记库：关注组织、来源与使用方式，通常不需要代码发布流程。
- 已有完整组织规则：链接和补充项目差异，先核对继承关系，不复制出多套互相冲突的政策。
- 用户只要目录方案：给职责与取舍，不因此初始化 Git、迁移文件或生成业务功能。

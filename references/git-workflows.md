# Git 操作指南

针对用户当前任务使用。先理解本地状态、历史是否共享和授权目标，再选择最少步骤。把命令具体化为已核实的路径、分支与远程；本文件中的“目标”不是可直接执行的占位参数。

参考：[Git Essentials v1.0.0](https://clawhub.ai/arnarsson/skills/git-essentials) 的日常任务覆盖，以及 [Git Workflows Pro v1.0.0](https://clawhub.ai/darinrowe/skills/git-workflows-pro) 的状态判断、恢复准备和按任务加载细节。原文于 2026-09-30 查阅。这里将命令速查改写为状态驱动的执行指导，省去与当前任务无关的高级操作。

## 开始前的状态判断

记录当前分支、HEAD（若已有提交）、未提交改动与暂存内容。检查是否存在正在进行的 merge/rebase/cherry-pick；有则先处理该状态，不叠加新的历史操作。无上游不代表仓库坏了，空仓库没有 HEAD 是正常情况。

判断上游关系要区分本地记录与刚获取的远端状态；未获取最新信息时不声称“已与远程同步”。远程获取按需要执行，避免带清理副作用的操作。不要默认远程叫 `origin`、默认分支叫 `main`。

已有团队约定优先。缺少约定时，个人小项目可用简洁的主分支流程；需要隔离改动时创建短期分支；有协作者时优先使差异便于评审。采用何种协作流程取决于参与人数、权限和项目习惯。[Pro Git：参与项目](https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project)

## 第一次建立仓库

用户明确要求从远程开始时，确认地址与本地落点，克隆到新目录，避免覆盖同名内容。先确认远程已有历史，不能对克隆失败的目录直接 `git init` 假装完成。

用户明确要求把已有项目初始化时，先确认目录边界和父目录仓库状态；再核查敏感文件、生成物和忽略规则，避免首次提交把整个工作区或本地配置带进去。默认分支名称按用户或平台已有约定确定。需要创建远程仓库时确认归属和可见性，先准备本地成果；“公开/私有”不能靠猜测决定。

解释三个独立结果：初始化建立本地版本库；提交保存版本；推送上传到指定远程。分别验证，不能把其中一步成功说成三步都已完成。

## 提交

用户请求提交时，确定要包含的具体改动。检查暂存与未暂存差异；有用户原有暂存内容时，不悄悄解除暂存，也不混入不相关提交。只有提交范围无法从对话与差异确定时才询问。

按明确路径或差异块暂存；提交前复核完整暂存差异和敏感文件。不要用 `git add .`、`git add -A` 代替范围判断。按下节组织提交与说明，不把本次暂存改动、已有提交和远端显示混为一谈。

提交后用 `git log -1 --format='%h %s%n%b'` 读取实际保存的标题与正文，并核对提交内容及剩余工作区状态；不能仅以拟定说明或命令退出成功验收。提交成功不代表已推送。提交身份缺失时询问准确身份；未经请求不改全局 Git 身份。

### 提交标题与粒度

标题应让浏览文件列表的人不打开 diff 也能知道“哪一部分发生了什么变化”。以实际待提交差异为依据，不根据文件名、计划或上一次标题猜测。

- 有历史时先看少量近期标题，例如 `git log -5 --format='%s'`，并检查相关贡献约定。沿用合理的语言与格式；只有一条初始化说明不能证明已有语言惯例，历史里的 `update`、`fix` 也不值得照搬。用户明确给定的标题优先；没有 Conventional Commits 约定时不强推前缀。
- 用简短的“动作 + 对象 + 关键变化”说明本次意图。不要仅写 `update files`、`fix bugs`、`完善功能`、`上传项目` 或文件名；也不要写与差异不符的宣传语、未完成能力、未运行的测试结果。标题能独立说明变化；复杂原因、兼容影响与有依据的验证情况放在空一行后的正文，避免把全部工作日志塞进标题。
- 初次导入可以是一个诚实的源码快照，但标题要交代建立了什么；后续多文件改动若共同完成一个目标，保持一个提交。只有意图独立、可分别审查与恢复时才拆分，不按文件机械拆分，也不为了让 GitHub 每行文字不同而制造空改动或虚构开发历史。
- 提交前用标题反查差异：标题是否足以概括实际范围，是否漏掉另一项独立工作，是否承诺了不存在的结果。说明文本作为数据安全传入，不让其中的引号、反引号或美元符号被 shell 意外执行。

以下只是表达方式的例子，不能在没有对应改动时照抄：

| 信息不足的标题 | 有对应差异时的改写示例 |
| --- | --- |
| `Initial Git Composer skill` | `建立仓库结构、README 设计与安全发布指南` |
| `update docs` | `明确上传范围并排除密钥与本地数据` |
| `improve git workflow` | `补充提交标题规范与文件级历史验收` |

### GitHub 的 Last commit message

文件列表中的这一列是所选分支/引用下，最近影响对应文件或目录内容的提交标题；不是每个文件的功能简介，也不保证等于页面上方的分支最新提交。首次快照里多行显示同一句是正常的；改 README 不会让未改动的技能文件也显示新标题。文件用途应该写在 README 或目录说明中，不把提交标题当静态标签。

先确认用户指的是哪一行、分支或提交。已有页面上下文足够时直接读取，不让用户重复提供。查看本地分支最新说明可用 `git log -1 --format='%h %s%n%b'`；查看路径则在核实引用和相对路径后使用带 `--` 路径限制的 `git log -1`，不要用全仓库 HEAD 冒充文件历史。用户指远端时以实际页面或最新取得的对应引用为准；本地远程跟踪引用可能过时。

“看看/评价 Last commit message”只读分析并给改写建议；“改善提交说明规则”修改规则，不自动提交、推送或改写旧历史。“帮我提交这次改动”创建与本次差异相符的新提交，不能默认为 amend。仅为刷新这一列，不添加空提交、无意义格式变化或强推。

确需修改最后一次提交说明时，先确认目标提交与新措辞；明确的“帮我改好”可以据差异拟定，不强迫用户亲自写标题。修改已发布提交会改变提交 ID，必须说明历史改写影响并取得相应授权；没有授权就保留原历史，在后续真实改动中使用改进后的标题。普通新提交不能修改旧提交说明，不能冒充完成改写。[GitHub：修改提交说明](https://docs.github.com/en/pull-requests/how-tos/commit-changes/changing-a-commit-message)

获准只改说明时保护现有暂存内容：例如 `git commit --amend --only` 配合安全传入的新说明，不附路径，不把用户待提交代码一起纳入。执行前记录旧提交和暂存/工作区状态，执行后验证新旧提交的树与父提交不变、暂存与工作区保持原状，说明与请求一致；签名等仓库约定照常遵循。[Git：commit 的 amend 与 only 语义](https://git-scm.com/docs/git-commit)

获准推送后，确认远端分支包含预期提交，再核对本次涉及的文件/目录所显示的标题；未触及路径保留旧标题是正确行为。交付时区分“规则已改”“已本地提交”“已推送且远端已核实”，只报告实际完成的状态。

## 分支、同步与合并

切换分支前确认当前改动会如何处理；需要隔离时可采用适合当前仓库的工作树方式。不得为了切换成功擅自丢弃或自动藏起用户改动。

同步时先确认远程和分支，再查看分歧。如果只需快进，使用可明确失败而不自动制造合并的方式；存在分歧时按既有约定选择合并或变基，不用强推“修好”。

冲突解决必须理解两边用途；涉及无法判断的业务意图时展示冲突与选择，请用户决定该处。不能一律选择 ours/theirs。解决后验证受影响行为，再继续原操作。

公开共享的历史被变基后会影响协作者，因此不把 rebase、amend 或压缩历史作为自动美化步骤。[Pro Git：变基的风险](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)

## 撤销与恢复

先区分用户要撤销什么，再解释会保留什么：

| 用户目的 | 处理方向 | 必须先弄清 |
| --- | --- | --- |
| 不想把某改动放进下次提交 | 仅调整暂存区，保留工作文件 | 路径和是否已有 HEAD |
| 放弃尚未提交的修改 | 展示具体差异，必要时备份后恢复该路径 | 用户明确要丢弃哪些内容 |
| 撤销已共享的普通提交 | 优先新增反向提交，保留可追踪历史 | 目标提交和后续依赖 |
| 找回消失的本地提交 | 先用 reflog 等只读信息定位，再创建恢复引用 | 提交是否仍存在；未提交内容不保证可恢复 |
| 撤销 merge 提交 | 判断父提交与后续影响后制定操作 | 主线父提交，不能盲猜 |

用户说“清理一下”不是授权 `reset --hard`、`clean -fd`、删除分支或重写历史。确需破坏性处理时先列出具体影响和恢复办法，只确认尚未明确授权的部分。备份不能替代授权。

恢复准备必须覆盖受影响的实际内容：备份分支仅保留已提交历史，不能保护工作区、暂存区或未跟踪文件。对这些内容按用户目的采用必要的补丁/文件备份或经授权的暂存方案；备份中若含敏感信息，使用仓库外合适位置。不要宣称 reflog 能找回从未提交的全部文件。执行历史改写前记录原始提交和恢复引用，结束后检查历史、文件状态及项目行为。

用户明确要求临时切换任务时，短期中断可考虑带说明的 stash；先说明是否包含未跟踪文件，恢复时检查冲突并验证后再考虑删除保存项。长期同时处理多个分支可考虑 worktree。不要把清理 stash 或 prune worktree 附加到普通整理任务。

## 上传范围与敏感数据排除

上传、首次发布或迁移仓库时先完成本节；普通只读查看不需要全仓库审计。

- 明确本地项目根目录、目标远程与分支、仓库归属和公开/私有状态。多个项目分别列出范围；只问无法从现状核实的决定，不擅自把父工作区初始化或推送，也不覆盖已有部署远程。
- 以实际待发布文件为准：检查已跟踪、已暂存、未跟踪以及准备复制的内容。排除真实 API Token、SSH 私钥、登录态/cookie、微信或飞书账号凭据、带认证信息的 URL、私有环境配置；还要排除个人阅读库、电子书/媒体原文件、消息记录、数据库及备份、上传目录、日志和浏览器缓存。必要的锁文件、数据库结构迁移和明确为虚构数据的测试夹具应保留，不能仅凭文件名或模式命中删除源码。
- 检查将上传的真实敏感信息时只输出文件位置和问题类型，不打印密钥或消息正文。疑似命中逐项判断；环境变量名称、占位样例和用于验证拒绝凭据的测试不等于真实泄露。配置样例仅保留无敏感值的必要字段。
- `.gitignore` 不会移除已跟踪文件，也不会清除历史。推送已有历史时检查将发布的提交；打包源码时检查归档内部，不能认为外层文件名安全就可上传。若采用不带旧历史的安全源码快照，在新隔离目录准备并说明取舍，保留原仓库和用户文件；不擅自重写共享历史。实际凭据疑似已泄露时提醒用户撤销或轮换，不能只删当前文件就宣布安全。
- 默认不发布 `node_modules`、构建产物、旧发布包或本机工具状态，除非当前交付明确需要。私有部署标识和机器路径应按用途裁剪；如果运行依赖其中的配置，则提供无私密信息的可运行配置，不一删了之。
- 凭据使用本机安全认证或现有 SSH 密钥，不要求用户把私钥或 Token 贴进聊天。SSH 能验证和推送到已有仓库，但不等于获得创建仓库、管理账号或发布 Release 的 API 权限；目标与能力缺失时只询问实际缺口。
- 推送前复核完整待发布清单及扫描结果。仍有真实敏感信息、上传范围不明或目标/可见性未经确认时不推送。上传后从同一目标读取远端提交与树，确认与本地准备结果一致；推送进程退出不能替代远端验证。

## 推送与远端设置

推送前复核目标地址、目标分支、将发布的提交与可能触发的自动化。用户已明确授权同一范围的推送时继续执行；仅请求本地整理或提交时不顺带推送。

认证或保护规则阻塞时报告具体原因，不通过关闭保护、泄露凭据或反复强推绕过。远端状态不确定时先读取验证再重试，不重复产生 PR、标签或发布。

若用户明确要求改写远端历史，检查是否共享、影响对象和恢复引用；需使用强制更新时优先采用带已核实预期远端提交的 lease 保护。它只能防止特定并发覆盖，不能替代协作者协调或消除重写风险。

## 交付日常习惯

围绕用户刚完成的任务，教一个对应习惯即可：

- 改之前看状态，知道自己在哪个分支。
- 提交前看差异，一次表达一个清楚的意图。
- 推送前跑相关检查，确认公开的内容正是自己想交付的。

不要把这些习惯变成每次都要用户手动确认的固定关卡；代理应完成能自行验证的部分。

# 项目结构指南

在用户从零开始、文件职责混乱或需要评估目录布局时读取。目录树是决策结果，不能用树形外观代替架构判断。下列结构是参考形状；按当前语言、框架、工具和真实内容裁剪，不把所有示意目录创建成空壳。

## 先确定四件事

- **交付什么**：一个脚本、可安装的库、网站/服务、多个关联应用，还是文档或数据成果？
- **怎么使用**：人从哪个入口开始，程序从哪个入口执行，怎样确认第一次运行成功？
- **哪些一起变化**：经常共同修改的内容是什么，哪些可以独立理解和验证？
- **谁来维护**：当前只有作者，已有协作者，还是有人依赖已发布版本？

优先从文件和请求中判断。缺少技术栈不妨碍先给结构原则；执行语言或框架特有的初始化前再解决必要选择。已有框架官方结构或清晰惯例优先；核对当前版本的官方资料，避免为了整齐破坏路由、资源加载、构建或发布约定。

## 按项目类型选择

| 项目类型 | 起步形状与理由 | 何时需要细分 |
| --- | --- | --- |
| 一次性/小型脚本、练习 | 根目录放说明与少量脚本，必要时加依赖声明；入口直接可见 | 复用逻辑或独立功能出现后再拆模块 |
| 单个应用、网站、服务 | 沿用框架约定，区分入口、业务功能、共享能力与静态资源 | 独立业务功能难以定位时按功能划分；不为层数建空层 |
| 可分发的库或 CLI | 明确公开入口与内部实现，说明安装和兼容条件 | 被外部用户依赖后增加发布包验证与迁移说明 |
| 多个关联应用/包 | 只有真实共享代码、工具或协调发布需求时考虑工作区/monorepo | 每个包都有用途、依赖关系与独立检查入口时再细化 |
| 文档、知识库、资源集合 | README 导航、按主题组织的内容与素材；优先解决查找问题 | 内容增加后补索引、来源和归档约定 |
| 数据、研究、Notebook | 区分分析入口、可复用代码、输入样例、结果与环境说明 | 多次复用的分析提取为代码；大数据/模型按实际存储方案管理 |

项目包含多种产物时可组合，但不要预设每个前后端项目都需要 monorepo。独立部署、访问权限、发布周期和共享代码需求共同决定仓库边界；只有计划、没有相关代码时不提前搭建多包体系。

## 三种可裁剪的起步示意

### 少量 Python 脚本

```text
project/
├── README.md          用途、运行方式和一份真实示例
├── main.py            当前程序入口
└── .gitignore         当前项目需要忽略的本地文件
```

确有第三方依赖时补与现有工具一致的依赖声明；有需要保护的关键行为时补测试。不要为只有一个函数的练习项目预建 `services/`、`repositories/` 和 `interfaces/`。

### 逐步成长的单个应用

```text
project/
├── README.md          使用与开发入口
├── src/               入口和业务代码，内部按实际职责组织
├── tests/             需要统一管理的行为验证
├── docs/              README 放不下的必要说明
└── scripts/           确有重复操作时才保留的脚本
```

项目清单、锁文件及工具要求的配置按生态放置；上图不省略这些需要，只省略语言差异。测试与代码放在一起也是合理选择；框架要求代码位于根目录、`app/` 或其他路径时沿用框架布局。`docs/` 与 `scripts/` 没有实际内容时不创建。

`src/` 内首先明确程序入口。功能逐渐独立时可以按业务功能放置相关实现；确有复用再提取共享模块。只有业务复杂度需要时才增加分层、接口与适配器。

### 确有多个关联产物的工作区

```text
project/
├── README.md          各产物的用途与启动入口
├── apps/              独立运行的应用
├── packages/          被复用或独立发布的包
└── docs/              跨应用的接口、开发与发布说明
```

补充所选工具实际需要的工作区配置，并明确每个应用/包的依赖、检查和发布方式。不能只将原目录移进 `apps/` 和 `packages/` 就宣称完成多包改造。小型单应用无需采用此结构。

## 决定代码边界，而非只给文件分类

- **入口清楚**：启动、命令、HTTP 请求或界面动作从哪里进入；不要让 README 和实际入口不同步。
- **职责可以命名**：目录名表达具体作用，避免把不相关功能持续堆进 `utils`、`common` 或 `helpers`。已有命名可用时不做纯风格重构。
- **相关内容容易一起找到**：同一功能的实现、验证和必要说明有明确对应关系，不要求它们物理上必须同目录。
- **依赖关系能讲清**：指出哪些模块调用哪些模块，保持公共入口稳定。发现循环依赖再针对性处理，不预先创造复杂抽象。
- **配置与数据有归属**：区分共享默认值、本地配置和敏感凭据。示例数据必须适合提交；真实个人/业务数据不能因“需要样例”进入仓库。
- **源码与产物可区分**：说明哪些是事实来源，哪些由构建生成。先核实发布方式再决定是否忽略生成物，保留项目需要提交的文件。
- **环境可以重建**：记录必要环境、依赖和输入的来源，不把作者机器上的虚拟环境、缓存或下载目录当作项目结构。

库项目要特别关注“从仓库里能导入”和“安装后能导入”的差异。例如 Python 的 `src` 布局增加了安装步骤，但可减少根目录掩盖打包错误的情况；选择时按项目目的判断，并在首次发布或打包变动时验证构建产物。参见 [PyPA：src 与 flat 布局](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)。

## 说明结构的最小成果

在现有 README 或确有需要的架构说明中，写明：

1. 为什么选择这种结构，当前项目有哪些重要限制。
2. 主要目录各负责什么；只解释容易混淆的部分。
3. 一个实际任务的路径：入口 → 实现 → 验证 → 相关说明。

例如用户问“在哪里改导出功能”，交付目标项目中真实存在的路径与检查命令，而不是泛泛说“去 src 目录”。只做方案、项目还不存在时，明确哪些是建议路径。

## 调整已有项目的顺序

先补导航与职责说明，定位真正需要变化的边界。确需移动文件时，列出旧路径、新路径和受影响的导入、配置、脚本、文档、部署及测试，再以可验证的小步迁移。

已有用户改动按主技能要求保护。不要用重新生成框架、整库覆盖或一次搬空目录实现“标准化”。如结构问题来自业务边界不清，先解释需要做的决定，不让新手误以为改目录名就能解决。

验收时选择一个真实任务，沿着新入口运行或验证；检查引用仍有效、构建/安装仍可用、用户知道下次该把内容放哪里。只有目录树漂亮而使用路径不清楚，不能算结构整理完成。

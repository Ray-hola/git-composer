# 元数据、许可证与徽章检查

用于整体体检、起步、专业化整理、完整 README 美化及结构化信息核对。目标是让用户看到的许可证、Python 等运行环境版本、发布信息和每个按钮都有依据、彼此吻合且可用。检查范围要完整，展示数量按项目需要裁剪。

## 先盘点，再对齐

确认本次对象是哪个仓库/子项目，以及工作树、开发分支还是已发布版本。查看 README 及其翻译、相关配置、CI、许可证、文档入口和可访问的托管信息；同时查内联链接、引用式链接、HTML 的 `src`/`href`、图片替代文本与标题。大型多包仓库只核对本次覆盖的包，但说明覆盖范围；包之间有意不同的版本和授权不能全局替换。

用一张工作表记录“信息项 → 权威依据及适用版本 → 出现位置 → 差异与处理 → 状态”。对下表逐项判断适用性，并盘点项目另有的结构化声明；不要把检查项直接变成要生成的文件或徽章清单。状态为已核实、已修正、待决定、未验证或不适用；缺资料不是不适用。工作表默认在对话中交付，沿用已有归档规则。

| 信息项 | 优先核对的证据 | 必须对齐的位置与含义 |
| --- | --- | --- |
| 项目身份 | 实际仓库地址、子项目清单、发布包元数据 | 名称、简介、Logo、源码链接、安装包名和导入/命令名；名字可以不同但要对应正确项目，不能残留模板作者或旧仓库地址 |
| 许可证与版权 | 适用的 `LICENSE*`、`COPYING*`、用户已明确的选择、必要的第三方声明 | README 授权段落和徽章、包许可证字段、授权范围及分发文件；核对完整文本、真实权利人和必要年份，保留已有版权，不自动改成当前用户 |
| 语言/运行环境 | 包兼容声明、运行配置、支持文档、测试证据 | README 前置条件、版本徽章、开发环境、容器和 CI 各自表达的支持/使用/测试范围 |
| 系统与外部条件 | 实际平台限制、系统依赖、服务和硬件要求 | Windows/macOS/Linux、浏览器、数据库、GPU 等声明；不根据作者机器或技术栈自动添加“全平台” |
| 包管理与依赖 | 项目现有清单、锁文件、工具版本配置 | README 安装方式、CI 安装步骤、开发说明及可选依赖；区分使用者安装与开发环境，不混用互不兼容的流程 |
| 安装与启动 | 已发布包、源码布局、实际脚本/入口和配置样例 | 执行目录、包名、extras、启动命令、必需配置；发布包安装、源码安装、容器使用各自可追溯，不为未发布项目写虚构安装入口 |
| 项目版本与发布渠道 | 版本事实来源、标签、Release、实际包注册表/下载产物 | README 版本、下载按钮、变化说明、包版本；标清稳定版/预发布/开发版，不能拿尚未发布的工作树版本冒充最新可安装版本 |
| CI 与质量状态 | 真实工作流、分支/事件、运行结果和报告 | Build/Test/Docs/Coverage 等徽章各对应什么检查及版本；无运行记录或无报告不能显示为通过或编造覆盖率 |
| 文档、演示与下载 | 实际存在且对目标读者可访问的页面/产物 | 按钮文字、目标版本、内容和权限一致；检查演示是否仍可用、下载是否对应所标系统与架构 |
| 贡献与反馈 | 已有贡献说明、Issue/Discussion 设置、安全反馈渠道 | CONTRIBUTING、Issues、Discussions、Security 等入口与真实流程一致；不虚构已关闭或不存在的渠道 |
| 多语言与导航 | 当前 README、标题锚点、文档目录 | 翻译切换、目录锚点、相对路径和图片大小写；标题或目录移动后同步修正相关入口 |
| 平台与发布页信息 | 可读取的 GitHub About/网站/Topics、包项目页、维护状态 | 描述、官网、文档、仓库链接、授权与状态不冲突；区分本地已改、远端待同步和无法查看 |

证据冲突时先确定各自覆盖的版本与用途；只有确认是过期展示才直接修正文案。不能通过修改许可证、扩大运行兼容范围或覆盖发布版本来迁就漂亮的徽章。维护者尚未决定的事项准确提出，其他独立项继续处理。

## 许可证：核对授权，保留范围

用户说“MIT 等用户协议”时按代码许可证理解；产品使用条款和隐私政策另按实际需求处理。已有明确选择沿用；新增、更换或遇到真实授权冲突时由用户决定，已在本轮或先前明确授权的选择不重复询问。没有许可证不能因为仓库公开就填 MIT 或宣称自由复用。[GitHub 许可证说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

核对许可证全文与准确标识、适用文件/产物和版权信息。保留代码、文档、数据、模型权重或第三方材料可能各自不同的授权；多许可证的组合含义不简化成一个好看的单许可证徽章。徽章链接到本项目实际授权说明或文件，通用许可证介绍不能替代项目的授权证据。平台未识别不等于没有许可证；先查看文件，不为出现标识而改写条款。

Python 包检查构建后端支持的许可证元数据格式、匹配的许可文件及必要分发内容。现行 `license` 的 SPDX 表达式与 `license-files` 需要对应实际分发授权；老项目先核对后端兼容性，局部文档任务不顺带升级整个打包工具链。有构建任务时核查实际产物，只有文件配置时不能声称已经随包分发。[PyPA 许可证场景](https://packaging.python.org/en/latest/guides/licensing-examples-and-user-scenarios/)

## Python 版本：分清三种含义

| 含义 | 常见证据 | 不能据此推断的内容 |
| --- | --- | --- |
| 声明支持/允许安装的范围 | `pyproject.toml` 的 `requires-python`，或实际使用的旧版/工具专用配置 | 声明本身不能证明每个版本已通过测试 |
| 开发时使用的版本 | `.python-version`、工具配置、容器、开发说明 | 一次本机运行或一个固定版本不能代表全部兼容范围 |
| 实际验证过的版本 | CI 矩阵与真实运行结果、本地隔离验证 | 矩阵配置存在不代表执行成功；只测一版不代表其他版已验证 |

按实际项目读取相关文件：`pyproject.toml`、已有 `setup.cfg`/`setup.py`、工具专用声明、环境锁定文件、tox/nox 配置、容器、CI 和 README。只读提取配置，不为获取元数据直接执行不明 `setup.py`。纯脚本没有打包配置时依据真实运行证据写明已验证环境，不能为了一个版本按钮创建不需要的发布结构。

兼容声明是事实来源，仍需与代码、依赖及验证证据交叉检查；PyPI classifiers 是展示/分类信息，安装限制由 `Requires-Python` 表达。工具的语法目标设置也不能代替运行验证。若 Python 徽章来自包注册表，核对其对应已发布包和元数据，与开发分支不同就标明区别。[PyPA 元数据指南](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)

例如声明 `>=3.10`、开发固定 `3.12`、CI 只在 `3.12` 通过，可以保留不同数字，但应记录其他声明版本缺少测试证据；不能由此写成“3.10 及以上均已测试”。若徽章却写 `3.9+`，则须纠正这一冲突。示例数字仅用于解释，不是本技能推荐版本；不为让文案一致擅自提高最低版本、收窄支持范围或新增上限。

其他生态同理：按实际工具读取 Node `engines`/`packageManager`/版本文件、Go 或 Rust 的版本与工具链声明等，区分运行要求、开发工具链和已验证平台，不按 Python 模板生成文件。

## 每个徽章和按钮都要验证

先选择信息，再选择样式。许可证与运行版本适用且已核实后提供清楚入口；有真实发布和 CI 时展示对应状态。下载量、Stars、赞助或社区徽章按用户需要选择，不凑数量。状态徽章与“开始使用 / 文档 / 演示 / 下载”等导航分组，同组统一样式、高度、Logo 用法与留白，保留状态颜色的含义；标签简短可读，窄屏自然换行。

对每个已有和新增项检查以下内容：

1. **显示值**：标签、版本范围、状态和单位符合证据。静态徽章用于已核实且可维护的信息；会变化的 CI/覆盖率使用真实数据源，不用静态绿色 `passing` 冒充结果。
2. **数据源**：图片 URL 的仓库、包名、工作流文件、分支、事件和发布渠道准确。GitHub 工作流徽章可限定分支和事件；默认分支没有运行时可能显示其他分支的最近结果，因此不能只凭绿图认定目标分支已通过。[GitHub 工作流徽章](https://docs.github.com/en/actions/how-tos/monitor-workflows/add-a-status-badge)
3. **点击目标**：图片能显示和点击正确是两项检查。许可证去本项目授权文件，CI 去对应运行/工作流，包版本去真实包/发布页，安装按钮去可用步骤；不以全部跳到仓库首页代替准确入口。GitHub Markdown 中使用外层链接包住图片；Shields 的 `link` 参数不能代替 Markdown 外层链接。[Shields 静态徽章](https://shields.io/badges/static-badge)
4. **编码与渲染**：检查 URL 中的范围比较符、空格、`+`、`#` 及服务特有的连字符规则；实际看最终文字，不只检查字符串。替代文本说明用途，图片失效后保留必要文字入口，明暗背景下可读。生成具体 URL 时核对该服务当前语法。[Shields Python 版本徽章](https://shields.io/badges/py-pi-python-version)
5. **目标内容**：检查页面或图片实际内容及权限，HTTP 200 也可能返回 `unknown`、`not found` 或错误项目。仅供登录者访问的入口应符合目标读者；受权限/网络限制时记为未验证，不自动删掉可能有效的私有入口。不要把私有 URL、令牌或内部路径传给公共徽章服务。

优先复用真实状态源；静态项目资料变更时同步维护，已有生成机制则修改其事实来源再生成。仅因徽章错误不新增 CI、发布包或修改远端配置；本地范围内修正文案与入口，必要远端动作按已有授权执行。

## 交付与维护

校验完成后回查所有受影响位置，包括多语言 README、包元数据、开发文档和实际预览。整体整理交付工作表摘要：哪些信息已对齐、依据在哪里、哪些仍待决定/未验证及原因。不把“文件存在”“链接成功”“视觉协调”合并成一个未经证明的全部通过。

版本、授权、仓库地址、安装命令、支持范围、工作流名称或发布渠道变化时，同步复查关联的徽章和按钮。只在重复漂移已造成问题或现有流程适合时添加自动检查；纯资料修订先完成准确核对，不强加一套新测试系统。

官方资料查阅日期：2026-10-01。具体项目实施时核实其工具版本和当前服务文档；本文不固定语言版本、徽章服务端点或许可证选择。

# README 设计指南

用于整体专业化整理和用户明确要求的首页升级。以 `beautify-github-readme` 为主要设计参考，用项目真实材料建立好看、协调且有辨识度的首页，让新访客迅速理解价值，并能完成第一次使用。已有设计优秀时保留；视觉质量是需要实际检查的交付结果。

参考来源（2026-09-30 查阅）：[beautify-github-readme 原始技能](https://github.com/oil-oil/beautify-github-readme/blob/main/skills/beautify-github-readme/SKILL.md)、[内容组织](https://github.com/oil-oil/beautify-github-readme/blob/main/skills/beautify-github-readme/references/content-architecture.md)、[视觉方向](https://github.com/oil-oil/beautify-github-readme/blob/main/skills/beautify-github-readme/references/visual-direction.md)、[GitHub 画布约束](https://github.com/oil-oil/beautify-github-readme/blob/main/skills/beautify-github-readme/references/github-readme-canvas.md)。借鉴其项目主题设计、证据优先与可维护素材思路；本技能自行选择适合新手的最小实现，不复制其推广或投稿流程。

2026-10-01 补充查阅：[项目主题头图](https://github.com/oil-oil/beautify-github-readme/blob/main/skills/beautify-github-readme/references/project-native-hero.md)、[SVG 制作与验收](https://github.com/oil-oil/beautify-github-readme/blob/main/skills/beautify-github-readme/references/svg-production.md)。本指南独立可用，无需为执行它安装或运行上游脚本。

## 确定本次范围

明确要求完整 README 时可调整内容和视觉；只要头图、示意图或其他素材时，保持 README 本身不变，交付素材与嵌入说明。用户已讲明范围就直接做；仅在无法判断是全文改版还是素材设计时问一个简短问题，同时继续阅读项目材料。

“把整个仓库整理专业”可以包含对 README 的合理改进；“只美化 README”不扩展到源码架构、CI 或 Git 历史。用户已指定风格时优先遵循。

## 用真实材料决定内容

查看现有说明、最小可运行例子、截图、结果文件和品牌材料，形成一个简短设计依据：谁会使用、他想完成什么、哪个实际结果最能说明价值、下一步在哪里开始。没有真实截图时，可使用已经核实的命令输出或清楚标注的流程图，不生成虚构的产品界面作证据。

首屏先建立理解，再展示一个可信结果，再引导首次使用；详细配置和开发信息按需要展开。已有使用者主要来查 API 或安装方式时，保留快捷入口。删除同一承诺的反复表达；功能、性能、用户量和维护状态以实际证据为准。

完整首页设计须读取 [元数据、许可证与徽章检查](metadata-and-badges.md)，先确认许可证、运行环境与发布信息，再设计徽章和按钮。保留安装、文档、演示等适用入口，逐个核对显示文字与点击去向；不要只复刻参考项目的徽章外观。

## 形成项目自己的视觉

优先延续已有 logo、界面色彩和产品语气。从内容中寻找可识别的形象：命令行工具可突出真实输入输出，数据项目可突出图表与来源，视觉工具可突出生成效果，知识库可突出导航与关联。

动手前简短说明选择的颜色、文字层级、信息密度和主要视觉材料，让用户知道设计为何适合项目。不为凑风格重复装饰。个人小工具的一张真实示例配清晰标题，也可以是完整方案。

把设计方向落实为可复用的小约定：背景/文字/强调色的用途，标题与正文的层级，图片与图表的对齐、边距和标注方式。样式应在整页保持一致；具体字体设计主要用于可控素材，正文使用 GitHub 支持的排版。用户提供喜欢的示例时，提炼其留白、密度、色彩和构图，再结合本项目内容设计。

每张图都应帮助理解某件事。把命令、参数、链接和需要频繁维护的文字留在 Markdown，便于复制、搜索和更新。避免把正文排成一张长图，也避免长篇文字挤在多列表格中。

## 设计整页，而非只添加一张图

按真实内容选择组件，不要求凑齐数量：

| 部位 | 设计决策 | 具体检查 |
| --- | --- | --- |
| 首屏标题与头图 | 名称、清楚的一句话和体现项目特点的材料协调组合；也可采用简洁文字标题 | 第一眼的重点明确，标题和展示材料有联系 |
| 实际效果展示 | 挑最能说明能力的截图、输入输出或成果；需要看细节时给它足够空间 | 不把完整界面缩成不可辨认的拼贴 |
| 状态与入口 | 展示适用且已核实的许可证、运行版本、发布与检查状态，安排文档和安装入口 | 标签/数据源/点击目标一致，同组样式协调，窄屏可换行 |
| 正文层级 | 内容分组、标题、段落长度和留白形成一致节奏 | 不出现大段密集文字、重复口号或层级混乱 |
| 流程与结构 | 确实有助于理解时使用简洁图表 | 图中关系符合项目，细节在正文可查 |
| 页尾与维护入口 | 必要的贡献、许可、支持信息保持清楚且收敛 | 找得到所需信息，风格与上文一致 |

首屏可以将标题与少量清晰成果合成，也可以把标题与大尺寸展示上下安排；看素材缩放后的效果再选择。缺少诚实的视觉证据时，用排版与项目相关的示意建立风格，不用虚构产品截图填满页面。图像生成可用于明确的主题表达，必须与真实产品效果区分。

设计完成后检查整页的重心和阅读顺序。过多颜色、重复装饰或每节都加图形标题让页面拥挤时，优先减少竞争元素；既有品牌本身鲜明时保留它的特征，不把所有项目改成同一种极简风格。

## 选择最容易维护的素材

优先复用真实截图、已有图形或简洁图表。需要定制标题与几何示意时可用可编辑 SVG；截图和复杂画面使用合适的位图。只有图像生成确实能表达项目主题且属于请求范围时才使用可用的图像工具，生成素材必须与真实产品证据区分。

默认静态呈现。只有用户需要表达动作或操作过程时才考虑动图，并保留静态替代内容。无需为普通 README 引入新的设计构建系统。

素材放入现有约定目录；没有约定时可用 `assets/readme/`。保存真正用于维护的源文件，避免把临时探索图、缓存和废弃版本都带入提交。

GitHub README 不能当作任意网页布局使用。依靠 Markdown、图片及简单嵌入；SVG 使用普通图形与文字，不依赖脚本、`foreignObject`、外部字体或远程图片引用。需要复杂合成时输出已经渲染并核验的图片，保留源层。图片要有表达用途的替代文本。

## 以预览验收

实际渲染修改后的 README 与所有新素材。可用约 900px 的桌面内容宽度和约 360px 的窄屏作为检查起点，再按实际页面调整；同时查看明暗背景下的可读性。SVG 字号要按最终显示比例判断，不能只看源文件数值；中文标题和多行说明须实际检查是否裁切。

对下列项目记录“通过 / 需要修正 / 未验证”，不以任意审美分数代替检查：

- **首屏**：项目名、一句话价值和下一步入口清楚，主要视觉能体现项目内容。
- **协调**：色彩、标题、图片和图表呈现一致，有清楚的主次与留白。
- **真实**：展示来自项目，说明图与真实截图分得清；徽章没有虚构状态。
- **一致**：按结构化信息指南核对每个许可证/版本/状态声明与按钮；多语言 README、安装说明和真实配置的含义吻合。
- **可读**：宽窄屏无明显裁切、溢出、难辨文字或过密拼贴，明暗背景下关键内容清楚。
- **可用**：命令可复制，导航有效，图片替代文本有意义；图片失效后仍能理解并开始使用。
- **可维护**：关键源素材保留，修改名称或截图不需要重做整页，无失效资源依赖。

发现问题后针对具体原因修改并重新渲染，直至本轮观察到的问题解决或明确说明阻塞。重要标签在窄屏无法阅读时拆分图形或移回正文。允许优秀的纯 Markdown 首页通过，图片数量和制作复杂度不是验收标准。

用一个新访客的问题验收：我知道它能帮我做什么吗？看到了可信结果吗？能找到第一步吗？隐藏图片后，核心说明、使用命令和链接仍应可用。

交付能直接查看的预览、修改后的 README、需要维护的素材及验证情况；改造已有页面时尽量用相同宽度展示前后效果，便于用户判断。说明采用的视觉方向和关键变化，用户给出审美反馈后围绕具体构图、色彩或密度继续修订，不以“检查通过”代替其偏好。

用户只请求素材时检查 README 未被改动。若没有渲染环境，交付可查看的源文件并明确视觉效果尚未验证；不要把 Markdown 语法检查说成视觉验收通过。发布仍按用户授权执行，不为获得线上截图擅自推送。

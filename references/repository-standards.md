# 整理判断与验收标准

仅阅读本次改动相关部分。以下是判断依据，不是逐项创建文件的清单。

整体规划先看 [项目结构指南](project-structure.md) 和 [治理与说明文件指南](governance-and-docs.md)；本文用于核查选定改动是否有效。

## README 与使用入口

让首次访问者能回答：项目解决什么、适合谁、怎样成功运行一次、结果在哪里、遇到问题怎么办。保留有价值的原文和已有语言风格；大幅内容移位前检查链接。

可按项目需要组织为：简介 → 实际示例 → 前置条件 → 安装与配置 → 运行 → 验证/开发 → 已知限制。已有短 README 足够时，不机械补齐章节。命令从实际清单和脚本提取；说明必要的环境变量名称，示例使用明确的假值。GUI 项目给操作路径，笔记仓库给导航与编辑方式。

需要提升首页呈现时读取 [README 设计指南](readme-design.md)，先确定真实内容和证据，再选择版式与素材。

验收：相对链接和引用文件存在，步骤顺序可执行，必要前置条件没有依赖作者机器的隐式设置。无法获取的截图、演示地址、测试结果不捏造。徽章必须指向真实可用的状态；没有对应服务时不增加。

许可证、运行版本、发布包、README 徽章和按钮按 [元数据、许可证与徽章检查](metadata-and-badges.md) 逐项核对。保留证据与未验证项，避免 README、项目配置、CI 与包注册表各说一套。

官方参考：[GitHub README 文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)说明了 README 的常见职责与相对链接用法。

## 目录与文件卫生

先识别入口、源码、测试、资源、文档、生成物的现有边界。目录改动必须解决真实困扰，例如入口找不到或生成文件混入提交；只有几个文件的脚本仓库可以保持扁平。

对于已难以导航的项目，先在现有文档补一张简短的“要做什么 → 去哪个文件/目录 → 如何验证”表，再判断是否真的需要搬文件。用真实的改动路径检验结构，而非根据目录名判断优劣。参见 [成熟仓库中的目录与贡献入口](mature-repositories.md)。

移动路径时同步检查导入、构建配置、脚本、文档链接、部署约定和测试。无法验证这些引用时缩小改动。不套用统一 `src/`、`tests/`、`docs/` 架构，不一次性制造大量空目录。

`.gitignore` 只收录适合该仓库的本地配置、缓存与生成物。框架需要提交的发布文件、迁移文件、测试样例和现有锁文件不能仅因“看起来像生成物”就删除。项目级规则写入项目，机器个人偏好不扩散到全局设置。

Git 不会因为新增忽略规则就停止跟踪已有文件。用 `git ls-files -- 路径` 判断跟踪情况；检查规则时可用 `git check-ignore -v --no-index -- 路径`，其中退出码 1 通常表示没有命中规则。需要停止跟踪时按已确认的具体路径处理，保留本地文件；不要执行全仓库清空索引再重加。[Git gitignore 文档](https://git-scm.com/docs/gitignore)

`.env.example` 只保留配置结构和假值；若 `.env*` 被忽略，确认例外规则确实允许提交样例。检查样例可被跟踪，以及真实本地配置仍被忽略。

发现疑似凭据时只报告位置与类型，不回显值。确认曾泄露的有效凭据需要撤销/轮换；移除当前文件和重写历史都不能替代轮换。历史清理、远程发布与凭据撤销分别处理授权，不在日常整理中顺手执行。

## 可复现与检查入口

从现有清单、锁文件、运行时配置和 CI 判断工具链。冲突证据先说明，不因多个锁文件并存就凭猜测删掉其中之一；可能属于不同子项目。

优先使用项目现有命令，例如它实际声明的启动、类型检查、测试和构建入口。只在缺少稳定入口导致重复出错时补一个薄封装。安装依赖前查看脚本行为，尽量使用隔离环境，避免升级全部依赖或修改全局运行时。

如果没有测试：先看是否有关键、稳定且可独立验证的行为；有就补最小回归验证，没有则给诚实的人工验收步骤。不要添加永远通过的测试、只检查自身写法的测试，或为练习仓库强装完整测试体系。

核心示例经常过时时，将实际示例文件纳入最小验证，文档引用或链接同一份示例，减少说明与代码分叉。已有文档/配置生成工具时修改事实来源并重新生成，检查差异；使用快照测试时逐项判断预期输出变化，不通过批量接受快照掩盖回归。参见 [FastAPI 与 Ruff 案例](mature-repositories.md)。

版本选择以仓库证据和当前官方文档为准，不在本技能固定某个语言版本、Action 版本或包管理器版本。离线时使用已核实的项目版本；未知兼容性标注为未验证。

## 自动检查（CI）

适用于需要反复验证的代码仓库。先延续已有平台；仅当平台已确定才生成平台配置。无远程平台的本地小项目可以只保留检查命令。

最小流水线复用本地可运行的检查：准备所需环境 → 按现有锁定策略安装 → 运行相关检查。矩阵、缓存、多平台和自动发布要有具体需求才添加。不要用 `continue-on-error`、吞错误或强制成功掩盖应失败的检查。

按路径跳过检查前确认文件的实际用途；Markdown 也可能承载可执行测试，不能把所有 `.md` 改动都视为纯说明。将部署、真实远端验收与常规检查区分，避免跑测试时顺带发布或修改外部资源。

GitHub Actions 的具体处理：

- 从真实分支与项目目录确定触发条件，不默认所有仓库主分支都叫 `main`。
- 按工作需要授予最小权限；普通检查一般只需要读取代码。
- 新引入 Action 时核实上游仓库与所用版本，优先固定到核实过的完整提交 SHA，并注明对应版本。无法核实 SHA 时不得编造或假称已固定。
- 来自外部 PR 的代码不能在带敏感凭据或写权限的上下文中执行；不要为了让外部 PR 检查通过而引入危险的 `pull_request_target` 用法。
- PR 标题、分支名等外部文本不能直接拼进 shell 命令。

以上安全行为见 [GitHub Actions Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)。增加具体工作流时按当前官方资料核对语法与兼容性。

验收分层：配置解析/静态检查、本地对应命令、实际远端运行。只完成前两项就如实写明远端待验证；推送执行不因生成了文件而自动获得授权。

## 协作与长期维护

文件选择、治理原则、责任与文档更新时机见 [治理与说明文件指南](governance-and-docs.md)。围绕实际贡献障碍选择最少措施，核对约定是否能被现有人员、工具和权限执行。

分支保护应与实际通过的检查名称和可用评审者匹配。个人仓库不应因为强制他人批准而被锁死。需要远端权限时先准备具体配置，再按用户授权执行。自动更新工具应能被实际维护，避免一次打开大量无人处理的依赖升级 PR。

当问题报告难以处理时，先约定复现所需的最少信息和状态，再考虑自动分流：确认是否重复、能否复现、影响多大、是否有替代方案。个人项目可先用“待补充 / 可处理 / 已完成”这类少量状态；不要照抄大型项目的标签矩阵或自动关闭时限。

## 持续发布

有实际发布需求时，先准备一份简短且可重复的发布步骤：确认目标提交与版本 → 运行相应检查和构建 → 准备变化说明与迁移事项 → 按授权发布 → 核实用户能获取并运行产物。小项目可以人工执行，重复成本明显时再自动化。参考 [Vite 与 GitHub CLI 的发布案例](mature-repositories.md)。

说明源码提交、版本号、标签和发布产物之间的对应关系。发布中断时先检查各平台已经完成哪一步，再处理未完成部分；不盲目重跑整条链路，不用覆盖已发布标签或删除版本作为默认恢复方式。发布脚本或工作流存在，不代表远端权限、审批设置和发布能力已经验证。

## 边界情境自查

- **只有一个 Python 脚本**：以准确运行说明、依赖与必要忽略规则为主；无需企业目录和发布流水线。
- **已有完整工程规范**：找真实失效点；允许结论为“当前已满足需求”，不要为了体现工作量增加文件。
- **暂存区有用户未完成的代码**：整理与该代码分开；不能用 `git add .` 或直接提交暂存区。
- **纯文档/笔记仓库**：关注导航、编辑与链接；缺少单元测试不算缺陷。
- **本地检查通过但未推送**：交付本地结果，远端 CI 状态为未验证。
- **旧环境才跑得通**：保留不确定性并定位缺失前置条件，不宣称新用户可复现。
